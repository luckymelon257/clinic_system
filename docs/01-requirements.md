# Система управління лікарнею — вимоги та функціонал

## 1. Опис предметної області

Багатопрофільна лікарня з **амбулаторною** (прийоми лікарів) та **стаціонарною** (госпіталізація у палати) частинами.
Система веде облік пацієнтів, персоналу, розкладу лікарів, записів на прийом, медичних записів (діагнози, рецепти,
аналізи), ліжкового фонду, а також виставлення рахунків з урахуванням страхового покриття.

**Стек:** PostgreSQL 16 · Node.js + Express · `pg` (node-postgres) · простий UI (серверний рендеринг).

## 2. Ролі користувачів

| Роль | Код | Основні можливості |
|---|---|---|
| Адміністратор | `admin` | Керування користувачами, відділеннями, палатами, довідниками; перегляд журналу аудиту; відновлення видалених записів |
| Реєстратор | `registrar` | Реєстрація/редагування пацієнтів, запис на прийом, скасування, госпіталізація та виписка |
| Лікар | `doctor` | Перегляд свого розкладу, проведення прийому, медичний запис, діагнози, рецепти, направлення на аналізи |
| Лаборант | `lab_technician` | Перегляд черги аналізів, внесення результатів |
| Касир | `cashier` | Рахунки, прийом оплат, звіти по виручці |
| Пацієнт | `patient` | Перегляд власних записів, історії хвороби, рахунків *(опційно)* |

## 3. Функціональні вимоги (фічі)

### 3.1 Користувачі та доступ
- **F-01** Автентифікація за email + пароль (bcrypt-хеш), сесія/JWT.
- **F-02** Рольова модель доступу (RBAC): кожен користувач має одну роль.
- **F-03** Деактивація користувача (`is_active`) та soft delete облікового запису.

### 3.2 Пацієнти
- **F-04** Реєстрація пацієнта (ПІБ, дата народження, стать, контакти, адреса, група крові, контакт для екстрених випадків).
- **F-05** Пошук пацієнтів за ПІБ / телефоном (нечіткий пошук, триграмний індекс).
- **F-06** Редагування даних пацієнта — фіксуються дата й автор останньої зміни.
- **F-07** Soft delete пацієнта та відновлення адміністратором.
- **F-08** Страхові поліси пацієнта (компанія, номер, термін дії, % покриття).
- **F-09** Повна медична історія пацієнта (прийоми, діагнози, рецепти, аналізи, госпіталізації).

### 3.3 Персонал і структура лікарні
- **F-10** Довідник відділень (з завідувачем) та спеціалізацій.
- **F-11** Облік лікарів (відділення, спеціалізація, номер ліцензії, вартість консультації).
- **F-12** Розклад роботи лікаря по днях тижня (години, кабінет).

### 3.4 Записи на прийом
- **F-13** Запис пацієнта до лікаря на конкретний час.
- **F-14** Перевірка доступності: час у межах розкладу лікаря, без перетину з іншими записами (обмеження на рівні БД).
- **F-15** Отримання вільних слотів лікаря на дату.
- **F-16** Зміна статусу: `scheduled → confirmed → in_progress → completed`, або `cancelled` / `no_show`.
- **F-17** Розклад на сьогодні для лікаря / відділення.

### 3.5 Медичні записи
- **F-18** Проведення прийому: створення медичного запису (скарги, огляд, висновок) — одною транзакцією разом з діагнозами та рецептом.
- **F-19** Діагнози за довідником МКХ-10 (основний / супутній).
- **F-20** Рецепт з кількома позиціями (препарат, дозування, частота, тривалість, кількість).
- **F-21** Медичні записи **не можна видаляти** (юридична вимога) — лише доповнювати.

### 3.6 Лабораторія
- **F-22** Направлення на аналізи (одне направлення — кілька тестів, пріоритет `routine`/`urgent`).
- **F-23** Внесення результату лаборантом; автоматична позначка «поза нормою» за референтними значеннями.
- **F-24** Черга незавершених аналізів.

### 3.7 Стаціонар
- **F-25** Палати (тип, місткість, вартість доби) та ліжка зі статусом.
- **F-26** Госпіталізація пацієнта на вільне ліжко; ліжко автоматично стає зайнятим.
- **F-27** Виписка: підсумок, звільнення ліжка, автоматичне формування рахунку.
- **F-28** Звіт заповненості ліжкового фонду по відділеннях.

### 3.8 Фінанси
- **F-29** Рахунок з позиціями (консультація, аналіз, перебування, препарат); сума перераховується автоматично.
- **F-30** Урахування страхового покриття при формуванні рахунку.
- **F-31** Прийом оплат (часткові оплати дозволені); статус рахунку оновлюється автоматично.
- **F-32** Список неоплачених/прострочених рахунків; звіт виручки по місяцях.

### 3.9 Аудит
- **F-33** Глобальний журнал змін (`audit_log`): хто, коли, що змінив (старі/нові дані у JSONB).
- **F-34** Автоматичне заповнення `created_at/created_by/updated_at/updated_by` тригерами; поточний користувач
  передається з коду в сесію БД через `set_config('app.current_user_id', …)`.

## 4. Бізнес-правила (обмеження на рівні БД)

| # | Правило | Як реалізовано |
|---|---|---|
| BR-1 | Лікар не може мати два записи, що перетинаються в часі | `EXCLUDE USING gist` на `appointments` |
| BR-2 | Одне ліжко — одна активна госпіталізація | `EXCLUDE USING gist` на `admissions` |
| BR-3 | Запис на прийом лише в межах розкладу лікаря | перевірка у `sp_book_appointment` |
| BR-4 | Не можна записати пацієнта / лікаря, позначеного видаленим | перевірка у процедурах + FK на активні записи |
| BR-5 | Медичні записи, діагнози, рецепти не видаляються | тригер `trg_forbid_delete` |
| BR-6 | `DELETE` для soft-delete сутностей перетворюється на soft delete | тригер `trg_soft_delete` (BEFORE DELETE) |
| BR-7 | Сума оплат не може перевищувати суму рахунку до сплати | перевірка у `sp_register_payment` |
| BR-8 | Email користувача унікальний без урахування регістру серед не видалених | частковий унікальний індекс по `lower(email)` |
| BR-9 | Дата виписки ≥ дати госпіталізації, кінець прийому > початку | `CHECK` обмеження |
| BR-10 | Відсоток страхового покриття 0–100 | `CHECK` обмеження |

## 5. Нефункціональні вимоги
- Уся робота з даними з коду — **лише через збережені процедури, функції та view** (без прямих `INSERT/UPDATE` у таблиці).
- Патерни **Repository + Unit of Work**: одна транзакція на бізнес-операцію, rollback при будь-якій помилці.
- Міграції у вигляді впорядкованих SQL-файлів; seed-дані для демонстрації.
- Валідація вхідних даних в API; централізована обробка помилок (помилки PostgreSQL → HTTP-коди).
