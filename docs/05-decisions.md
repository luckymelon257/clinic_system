# Рішення та відхилення від специфікації

Формат: **D-xx** — що в специфікації → що зроблено → чому.

- **D-01** Стек у `01-requirements.md` / `03-architecture.md` — Express + EJS (серверний рендеринг) → React + Vite SPA у `apps/web`, API у `apps/api`, монорепо pnpm + Turborepo. Причина: затверджене завдання на реалізацію; бізнес-поведінка не змінюється.
- **D-02** Node 22 → локально доступний Node 20.20; код сумісний з 22 (`.nvmrc` = 22, `engines.node >= 20`).
- **D-03** Порт Postgres 5432 → 5434 на хості (5432/5433 зайняті іншими проєктами на машині розробника). Контейнер усе одно `postgres:16` на 5432 всередині.
- **D-04** `@clinic/contracts` постачається як TypeScript-джерело без кроку збірки; API збирається бандлером, web — Vite.
- **D-05** Кастомні SQLSTATE: `P0002` (збігається з вбудованим `no_data_found`) використовується як «не знайдено» → HTTP 404; `P0403` → 403, `P0409` → 409; решта `P0xxx` → 422. Специфікація каже лише «P0001..P0099 → 409/422».
- **D-06** Роль `patient` (опційна у специфікації) має демо-обліковий запис і вхід, але окремого кабінету пацієнта немає.
- **D-07** До view додано ті, яких немає у §5, але потрібні UI/API (напр. per-bed `v_beds`, довідники) — додавання, не зміна поведінки.
- **D-08** `fn_patient_age(p_dob, p_on date DEFAULT current_date)` — додатковий параметр, бо `IMMUTABLE`-функція не може читати `current_date`.
- **D-09** BR-3: початок прийому має також лежати на сітці слотів розкладу. Додано допоміжні `fn_is_within_schedule`, `fn_assert_patient_active`, `fn_assert_doctor_active`. BR-4 «FK на активні записи» в PG неможливий напряму — перевірка у процедурах.
- **D-10** `sp_lab_result_record` повертає id результату через `INOUT p_id` (у специфікації без нього).
- **D-11** `sp_invoice_generate_for_admission` одразу виставляє рахунок (`issued`), щоб виписку й оплату можна було провести в одному UoW; рахунок з нульовою сумою до сплати стає `paid`.
- **D-12** Прийом може перейти в `completed` напряму зі `scheduled`/`confirmed` (через `sp_medical_record_create`).
- **D-13** Переведення (`sp_transfer_patient`) змінює ліжко існуючої госпіталізації; EXCLUDE по ліжку враховує лише активні госпіталізації, у пацієнта — максимум одна активна.
- **D-14** Видалення захищеного запису (BR-5) → SQLSTATE `P0403`; таблиця поза білим списком soft delete → `22023`.
- **D-15** `audit_log` ніколи не зберігає `password_hash`; `changed_at` бере `created_at/updated_at` рядка, тож seed-історія має історичні дати.
- **D-16** 27 таблиць замість 26: окрема `lab_order_items` (тести у направленні) і `lab_results`; `users.role_id` → таблиця `roles`, `v_users.role` віддає код ролі.
- **D-17** Rollback-тест `VisitService.complete` підміняє останній крок (`vi.spyOn(InvoiceRepository.prototype, 'issue')` → справжній `sp_invoice_issue(-1)`), а не тестовий хук у продакшн-коді.
- **D-18** Неактивний користувач отримує 401 і при вході, і на наступних запитах (кожен запит перечитує `v_users`).
- **D-19** Playwright e2e — окремий пакет `apps/e2e` і скрипт `pnpm e2e` (потребує запущеної бази), не входить у `pnpm test`. Версія `@playwright/test` 1.62.1 — під попередньо встановлений браузер.
- **D-20** Немає окремого view для всіх направлень на аналізи: `v_lab_queue` показує лише незавершені, результати — `v_lab_results`.

## Лаб 2 (NoSQL)

- **D-21** Кімнат у схемі немає (лише текст `doctor_schedules.room`) → нова таблиця `rooms` і nullable `beds.room_id`; існуючі ліжка довідника отримують по одній кімнаті на палату.
- **D-22** Медсестер у схемі немає → таблиця `staff` (лікар або медсестра, без облікового запису) і `staff_shifts`; роль `nurse` у `user_role` не додається.
- **D-23** Синхронізація графа — transactional outbox (тригери пишуть у `graph_outbox` у тій самій транзакції), воркер застосовує ідемпотентно (`MERGE` за id); початкове завантаження — повний ETL. Прийнятне відставання ≤ 5 с.
- **D-24** Перетин інтервалів обчислюється під час запиту в обох рушіях (сирі факти присутності, без матеріалізованих ребер «контакт») — інакше порівняння нечесне.
- **D-25** Трасування повертає для кожної особи мінімальну кількість кроків; часова послідовність контактів (B після A) не вимагається — достатньо перетину в межах вікна. Обмеження задокументоване в загрозах валідності.
- **D-26** Neo4j Community має одну базу на інстанс → окремі контейнери `neo4j` (основний/бенч) і `neo4j-test` замість баз на агента.
- **D-27** Відкликання JWT — окремий ключ на `jti` з `EX`, а не множина (у членів множини немає власного TTL).
- **D-28** Якщо Redis недоступний: кеш і лічильники читаються з PostgreSQL, перевірка відкликання — fail-open з логом і локальною пам'яттю процесу; якщо недоступний Neo4j: трасування → 503 `GRAPH_UNAVAILABLE`.
- **D-29** Середовище перевірки W0 — хмарний контейнер без Docker → ті самі рушії запущено нативно на портах compose: PostgreSQL 16 (кластер з налаштуваннями `command:` сервісу `db` і локаллю `C.UTF-8`, бо `pg_trgm` при `lc_ctype = C` не будує триграм для кирилиці), Neo4j 5.26.33 і Redis 7.4.12 — бінарні файли з офіційних образів `neo4j:5.26-community` / `redis:7.4` (heap / page cache / AOF / maxmemory як у compose). `docker-compose.yml` лишається еталоном; ліміти CPU/RAM у такому прогоні не діють, і результати бенчмарку це фіксують (`environment.containers`).
- **D-30** Контакт (крок) = обидві присутності перетинають вікно `[from, to)` і перетинаються між собою (`x.f < y.t AND y.f < x.t`); за теоремою Геллі для відрізків це те саме, що спільна точка x, y і вікна. Межі напіввідкриті: присутності «впритул» — не контакт.
- **D-31** `sp_transfer_patient` змінює ліжко існуючої госпіталізації (D-13) → присутність усієї госпіталізації — у поточній кімнаті / палаті. Однаково в `v_presence` і графі, тож на еквівалентність не впливає; це загроза валідності моделі, не порівняння.
- **D-32** Подія outbox — знімок поточного стану рядка-джерела; для присутності — усі ребра джерела (`src`, `srcId`), воркер замінює їх цілком (видалити ребра джерела → створити з payload). Тому повторне застосування ідемпотентне, а скасований прийом дає порожній список ребер. Ліжко без `room_id` отримує першу кімнату палати (тригер), тож довідник Лаб 1 автоматично має по кімнаті на палату (D-21).
- **D-33** Взаємодії: перевіряються пари, де хоча б один препарат — новий; пара двох поточних препаратів не повторюється. Рядок відповіді — на кожне джерело (пряма пара і кожна пара класів), `classA` — клас препарату з меншим id. Клас–клас зберігається з `class_a <= class_b`; `class_a = class_b` — дублювання терапії.
- **D-34** Маршрути Лаб 2 додано в контракт у W0; щоб `apps/api` і `apps/web` компілювались до W2, у них додано заглушки (`apps/api/src/lab2-pending.ts`, блок у `apps/web/src/mocks/handlers.ts`), що повертають 503 / 500 «Ще не реалізовано». W2 замінює їх реальними обробниками.
- **D-35** Версії клієнтів: `neo4j-driver` 5.28.3 (лінія 5.x, як сервер 5.26 LTS), `redis` 5.12.1 (5.12.2 опубліковано менш ніж 2 тижні тому).

### graph-neo4j

- **D-40** Трасування і найкоротший ланцюг у Neo4j — пошук у ширину (BFS) у Cypher, по одному рівню на крок (рівні розгорнуто в тексті запиту, глибина — перевірене ціле 1…8), замість QPP + `ANY SHORTEST`. Причина: шляхи Cypher 5 не повторюють ребро (DIFFERENT RELATIONSHIPS), а ланцюг контактів законно проходить через ту саму присутність двічі (P3 потрапляє через своє перебування в W1 і через нього ж передає S1) — форма `ANY SHORTEST` пропускала таких осіб (golden T1/T2/T5/Q2/Q9). `REPEATABLE ELEMENTS` є лише в Cypher 25 (Neo4j 2025.x). На кожному рівні присутності фронту групуються за місцем, кожне місце розгортається один раз, `seen` гарантує мінімальну кількість кроків.
- **D-41** Ідентифікатори й час (epoch ms) пишуться і передаються в Neo4j як INTEGER (`neo4j.int`): драйвер JS надсилає числа як FLOAT, і без цього властивості й порівняння були б дробовими.
- **D-42** Повний ETL читає PG в одному знімку `REPEATABLE READ` через серверні курсори (пачки по 10 000, наступна пачка читається, поки Neo4j пише поточну) і підтверджує саме ті події outbox, що були видимі в знімку (а не всі з `id <=` максимального: транзакція з меншим id могла закомітитись пізніше).
- **D-43** Свідок кроку (`parentKind/parentId/exposure/placeId`) обирається за силою контакту: кімната > кабінет > палата. На еквівалентність не впливає (порівнюються лише `(особа, кроки)`).
- **D-44** Індекси Neo4j: обмеження унікальності `id` на кожній мітці (крім `:Person` — id пацієнтів і персоналу перетинаються), індекс `PRESENT(src, srcId)` для заміни ребер джерела воркером, `TAKES(rxId)`. Індексу на `PRESENT(f, t)` немає: обхід іде від вузла по його ребрах, а реляційний діапазонний індекс Neo4j служить лише глобальному пошуку за властивістю. Наслідок (видно в PROFILE): місце з великою кількістю присутностей (кабінет лікаря за 2 роки) розгортається повністю, фільтр за часом — після розгортання; у PG той самий крок — GiST за (місце, період).
- **D-45** Подія outbox `office` не містить імені лікаря, тож у вузла `:Office`, створеного воркером, немає `name` (повний ETL його заповнює). Це лише підпис у UI; гейти порівнюють id і ребра.
