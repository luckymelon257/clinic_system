# Рішення та відхилення від специфікації

Формат: **D-xx** — що в специфікації → що зроблено → чому.

- **D-01** Стек у `01-requirements.md` / `03-architecture.md` — Express + EJS (серверний рендеринг) → React + Vite SPA у `apps/web`, API у `apps/api`, монорепо pnpm + Turborepo. Причина: затверджене завдання на реалізацію; бізнес-поведінка не змінюється.
- **D-02** Node 22 → локально доступний Node 20.20; код сумісний з 22 (`.nvmrc` = 22, `engines.node >= 20`).
- **D-03** Порт Postgres 5432 → 5434 на хості (5432/5433 зайняті іншими проєктами на машині розробника). Контейнер усе одно `postgres:16` на 5432 всередині.
- **D-04** `@clinic/contracts` постачається як TypeScript-джерело без кроку збірки; API збирається бандлером, web — Vite.
- **D-05** Кастомні SQLSTATE: `P0002` (збігається з вбудованим `no_data_found`) використовується як «не знайдено» → HTTP 404; `P0403` → 403, `P0409` → 409; решта `P0xxx` → 422. Специфікація каже лише «P0001..P0099 → 409/422».
- **D-06** Роль `patient` (опційна у специфікації) має демо-обліковий запис і вхід, але окремого кабінету пацієнта немає.
- **D-07** До view додано ті, яких немає у §5, але потрібні UI/API (напр. per-bed `v_beds`, довідники) — додавання, не зміна поведінки.
- **D-08** `fn_patient_age(p_dob, p_on date DEFAULT current_date)` — додатковий параметр, бо `IMMUTABLE`-функція не може читати `current_date`.
- **D-09** BR-3: початок прийому має також лежати на сітці слотів розкладу. Додано допоміжні `fn_is_within_schedule`, `fn_assert_patient_active`, `fn_assert_doctor_active`. BR-4 «FK на активні записи» в PG неможливий напряму — перевірка у процедурах.
- **D-10** `sp_lab_result_record` повертає id результату через `INOUT p_id` (у специфікації без нього).
- **D-11** `sp_invoice_generate_for_admission` одразу виставляє рахунок (`issued`), щоб виписку й оплату можна було провести в одному UoW; рахунок з нульовою сумою до сплати стає `paid`.
- **D-12** Прийом може перейти в `completed` напряму зі `scheduled`/`confirmed` (через `sp_medical_record_create`).
- **D-13** Переведення (`sp_transfer_patient`) змінює ліжко існуючої госпіталізації; EXCLUDE по ліжку враховує лише активні госпіталізації, у пацієнта — максимум одна активна.
- **D-14** Видалення захищеного запису (BR-5) → SQLSTATE `P0403`; таблиця поза білим списком soft delete → `22023`.
- **D-15** `audit_log` ніколи не зберігає `password_hash`; `changed_at` бере `created_at/updated_at` рядка, тож seed-історія має історичні дати.
- **D-16** 27 таблиць замість 26: окрема `lab_order_items` (тести у направленні) і `lab_results`; `users.role_id` → таблиця `roles`, `v_users.role` віддає код ролі.
- **D-17** Rollback-тест `VisitService.complete` підміняє останній крок (`vi.spyOn(InvoiceRepository.prototype, 'issue')` → справжній `sp_invoice_issue(-1)`), а не тестовий хук у продакшн-коді.
- **D-18** Неактивний користувач отримує 401 і при вході, і на наступних запитах (кожен запит перечитує `v_users`).
- **D-19** Playwright e2e — окремий пакет `apps/e2e` і скрипт `pnpm e2e` (потребує запущеної бази), не входить у `pnpm test`. Версія `@playwright/test` 1.62.1 — під попередньо встановлений браузер.
- **D-20** Немає окремого view для всіх направлень на аналізи: `v_lab_queue` показує лише незавершені, результати — `v_lab_results`.

## Лаб 2 (NoSQL)

- **D-21** Кімнат у схемі немає (лише текст `doctor_schedules.room`) → нова таблиця `rooms` і nullable `beds.room_id`; існуючі ліжка довідника отримують по одній кімнаті на палату.
- **D-22** Медсестер у схемі немає → таблиця `staff` (лікар або медсестра, без облікового запису) і `staff_shifts`; роль `nurse` у `user_role` не додається.
- **D-23** Синхронізація графа — transactional outbox (тригери пишуть у `graph_outbox` у тій самій транзакції), воркер застосовує ідемпотентно (`MERGE` за id); початкове завантаження — повний ETL. Прийнятне відставання ≤ 5 с.
- **D-24** Перетин інтервалів обчислюється під час запиту в обох рушіях (сирі факти присутності, без матеріалізованих ребер «контакт») — інакше порівняння нечесне.
- **D-25** Трасування повертає для кожної особи мінімальну кількість кроків; часова послідовність контактів (B після A) не вимагається — достатньо перетину в межах вікна. Обмеження задокументоване в загрозах валідності.
- **D-26** Neo4j Community має одну базу на інстанс → окремі контейнери `neo4j` (основний/бенч) і `neo4j-test` замість баз на агента.
- **D-27** Відкликання JWT — окремий ключ на `jti` з `EX`, а не множина (у членів множини немає власного TTL).
- **D-28** Якщо Redis недоступний: кеш і лічильники читаються з PostgreSQL, перевірка відкликання — fail-open з логом і локальною пам'яттю процесу; якщо недоступний Neo4j: трасування → 503 `GRAPH_UNAVAILABLE`.
- **D-29** Середовище перевірки W0 — хмарний контейнер без Docker → ті самі рушії запущено нативно на портах compose: PostgreSQL 16 (кластер з налаштуваннями `command:` сервісу `db` і локаллю `C.UTF-8`, бо `pg_trgm` при `lc_ctype = C` не будує триграм для кирилиці), Neo4j 5.26.33 і Redis 7.4.12 — бінарні файли з офіційних образів `neo4j:5.26-community` / `redis:7.4` (heap / page cache / AOF / maxmemory як у compose). `docker-compose.yml` лишається еталоном; ліміти CPU/RAM у такому прогоні не діють, і результати бенчмарку це фіксують (`environment.containers`).
- **D-30** Контакт (крок) = обидві присутності перетинають вікно `[from, to)` і перетинаються між собою (`x.f < y.t AND y.f < x.t`); за теоремою Геллі для відрізків це те саме, що спільна точка x, y і вікна. Межі напіввідкриті: присутності «впритул» — не контакт.
- **D-31** `sp_transfer_patient` змінює ліжко існуючої госпіталізації (D-13) → присутність усієї госпіталізації — у поточній кімнаті / палаті. Однаково в `v_presence` і графі, тож на еквівалентність не впливає; це загроза валідності моделі, не порівняння.
- **D-32** Подія outbox — знімок поточного стану рядка-джерела; для присутності — усі ребра джерела (`src`, `srcId`), воркер замінює їх цілком (видалити ребра джерела → створити з payload). Тому повторне застосування ідемпотентне, а скасований прийом дає порожній список ребер. Ліжко без `room_id` отримує першу кімнату палати (тригер), тож довідник Лаб 1 автоматично має по кімнаті на палату (D-21).
- **D-33** Взаємодії: перевіряються пари, де хоча б один препарат — новий; пара двох поточних препаратів не повторюється. Рядок відповіді — на кожне джерело (пряма пара і кожна пара класів), `classA` — клас препарату з меншим id. Клас–клас зберігається з `class_a <= class_b`; `class_a = class_b` — дублювання терапії.
- **D-34** Маршрути Лаб 2 додано в контракт у W0; щоб `apps/api` і `apps/web` компілювались до W2, у них додано заглушки (`apps/api/src/lab2-pending.ts`, блок у `apps/web/src/mocks/handlers.ts`), що повертають 503 / 500 «Ще не реалізовано». W2 замінює їх реальними обробниками.
- **D-35** Версії клієнтів: `neo4j-driver` 5.28.3 (лінія 5.x, як сервер 5.26 LTS), `redis` 5.12.1 (5.12.2 опубліковано менш ніж 2 тижні тому).

### W1 graph-sql (міграція 010, генератор, гейт щільності)

- **D-36** Нові SQLSTATE для BR-12: `P0080` глибина поза 1…5 (шлях 1…8), `P0081` `from >= to`, `P0082` вікно > 90 днів, `P0083` невідомий тип особи → HTTP 422.
- **D-37** `fn_trace_contacts_cte` навмисно «підручниковий»: рекурсивний CTE з `CYCLE` не повертається до особи на тому самому шляху, але різні шляхи до однієї особи не зливаються, тож кількість проміжних рядків росте з глибиною (×1: d2 0.23 с, d3 36 с). Це і є порівнюваний «наївний SQL»; оптимізований SQL — BFS нижче.
- **D-38** `fn_trace_contacts` / `fn_exposure_path` — BFS на PL/pgSQL зі станом у тимчасових таблицях сесії (`_graph_bfs`, `_graph_pres`), тому функції `VOLATILE`. Кожен рівень — один set-based запит: фронт ≤ 32 осіб (`clinic.bfs_small_frontier`) — індексні кроки по джерелах (`fn_person_presence` → `fn_place_presence`, GiST «місце + період»); більший фронт — присутності вікна матеріалізуються один раз на виклик (сирі факти, не ребра-контакти — D-24). Причина: планувальник не проштовхує параметризовані умови крізь `UNION ALL`-view з обчислюваними колонками і завжди хешує все вікно (≈ 80 мс навіть для однієї особи). Свідок кроку детермінований: room > office > ward, далі найменший батько, місце, час.
- **D-39** Бенч-бази `clinic_bench_x{N}` без seed-ів Лаб 1: генератор створює лише те, що потрібно графу й бенчмаркам (без діагнозів, лабораторії, рахунків, полісів; користувачі — лише облікові записи лікарів). Довідник ліків (600 / 80 / 550) спільний для мережі, не множиться на N. Час — місцевий `Europe/Kyiv`, без меж у 03:00–04:00.
- **D-40** Змін персоналу ×1 ≈ 101 k замість ≈ 85 k: 85 k = ротація медсестер (82 k) + чергування (2.9 k); палатні зміни лікарів 08–16 у будні (15.7 k) додано, щоб лікуючий лікар мав зміни під час госпіталізації. Чергування вихідного дня — дві зміни 08–20 і 20–08, бо 24-годинна зміна в ніч переходу на зимовий час триває 25 год і порушує `ck_staff_shifts_length`.
- **D-41** `COPY … FROM STDIN` реалізовано власним Submittable для `pg` (`gen/copy.ts`) замість залежності `pg-copy-streams`.
- **D-42** Гейт щільності рахує d1–d3 на 200 індексних пацієнтах; d5 (насичення, дорогий) — на всіх 200 для ×1 і на 30 для ×5 / ×10. Додатково на реальних даних перевіряється CTE = BFS на глибині 2.
- **D-43** S5: `fn_admissions_by_dept_month` групує за місяцем `admitted_at` у `[from, to)`; додано B-tree `ix_admissions_admitted_at` (у Лаб 1 часового індексу на admissions не було), щоб плоский агрегат у PG був чесно проіндексований.
### graph-neo4j

- **D-44** Трасування і найкоротший ланцюг у Neo4j — пошук у ширину (BFS) у Cypher, по одному рівню на крок (рівні розгорнуто в тексті запиту, глибина — перевірене ціле 1…8), замість QPP + `ANY SHORTEST`. Причина: шляхи Cypher 5 не повторюють ребро (DIFFERENT RELATIONSHIPS), а ланцюг контактів законно проходить через ту саму присутність двічі (P3 потрапляє через своє перебування в W1 і через нього ж передає S1) — форма `ANY SHORTEST` пропускала таких осіб (golden T1/T2/T5/Q2/Q9). `REPEATABLE ELEMENTS` є лише в Cypher 25 (Neo4j 2025.x). На кожному рівні присутності фронту групуються за місцем, кожне місце розгортається один раз, `seen` гарантує мінімальну кількість кроків.
- **D-45** Ідентифікатори й час (epoch ms) пишуться і передаються в Neo4j як INTEGER (`neo4j.int`): драйвер JS надсилає числа як FLOAT, і без цього властивості й порівняння були б дробовими.
- **D-46** Повний ETL читає PG в одному знімку `REPEATABLE READ` через серверні курсори (пачки по 10 000, наступна пачка читається, поки Neo4j пише поточну) і підтверджує саме ті події outbox, що були видимі в знімку (а не всі з `id <=` максимального: транзакція з меншим id могла закомітитись пізніше).
- **D-47** Свідок кроку (`parentKind/parentId/exposure/placeId`) обирається за силою контакту: кімната > кабінет > палата. На еквівалентність не впливає (порівнюються лише `(особа, кроки)`).
- **D-48** Індекси Neo4j: обмеження унікальності `id` на кожній мітці (крім `:Person` — id пацієнтів і персоналу перетинаються), індекс `PRESENT(src, srcId)` для заміни ребер джерела воркером, `TAKES(rxId)`. Індексу на `PRESENT(f, t)` немає: обхід іде від вузла по його ребрах, а реляційний діапазонний індекс Neo4j служить лише глобальному пошуку за властивістю. Наслідок (видно в PROFILE): місце з великою кількістю присутностей (кабінет лікаря за 2 роки) розгортається повністю, фільтр за часом — після розгортання; у PG той самий крок — GiST за (місце, період).
- **D-49** Подія outbox `office` не містить імені лікаря, тож у вузла `:Office`, створеного воркером, немає `name` (повний ETL його заповнює). Це лише підпис у UI; гейти порівнюють id і ребра. **Усунуто** міграцією `012_graph_outbox_office_name.sql`: подія `office` тепер несе `name`, воркер його записує.

### redis (W1)

- **D-50** Лічильники ліжок: `HINCRBY` після commit + звірка `reconcile()` з `v_beds` (перезапис одним `MULTI`). `HINCRBY`, що встиг між читанням PG і `EXEC` звірки, перезаписується — наступна звірка це виправляє (API запускає звірку при старті й періодично). Додатковий ключ `beds:reconciled_at` (немає в docs/06 §5) — для `BedCounts.reconciledAt`. Ліжка `maintenance` не рахуються ні вільними, ні зайнятими.
- **D-51** Тріаж: член ZSET — id з нулями попереду (12 цифр), щоб при однаковому score (той самий ESI і та сама мілісекунда) виклик ішов за id, а не лексикографічно. Після `ZPOPMIN` хеш запису лишається до кінця свого TTL 24 год (історія); `position` = `ZRANK + 1`.
- **D-52** ICU: два шляхи алертів — pub/sub `<prefix>:alerts:critical` (миттєво, без гарантії доставки, для SSE) і група споживачів `alert-persister` на `icu:vitals` (надійно: `XACK` лише після `CALL sp_icu_alert_record`, завислі записи перехоплює `XAUTOCLAIM` через 30 с). Записи потоку мають поля `alert` і `violations`; хеш `icu:latest:{bedId}` — ще `streamId` і `alert`. `MAXLEN ~ 100000` обрізає цілими вузлами, тож довжина може трохи перевищувати 100 000.
- **D-53** Пороги BR-17 — строгі нерівності, як записано (`< 40` спрацьовує на 39, не на 40); для діастолічного тиску порогу немає. Єдине визначення — `fn_icu_violations` (011); Lua-скрипт повторює його в тому самому порядку, тест перевіряє збіг на кожній межі.
- **D-54** `triage_queue_pg`, `fn_triage_pop`, `icu_vitals_pg`, `sp_icu_vitals_insert` — еталони PG лише для бенчмарків R3/R4 і тестів (не `apps/api`); `fn_triage_pop` — функція, бо має повернути рядок. На таблиці 011 аудит-тригери не ставляться: автора-користувача немає, частота висока. `sp_icu_vitals_insert` робить `pg_notify` — аналог `PUBLISH`, щоб порівнювалась однакова робота.
- **D-55** Параметри `sp_icu_vitals_insert` — `numeric` (неявного приведення `real → numeric` немає); колонки `icu_vitals_pg` — `real`.
- **D-56** Клієнт Redis створюється з `disableOfflineQueue` і обмеженим перепідключенням: при недоступному Redis команди падають одразу (інакше чекали б у черзі клієнта), що й дає деградацію D-28. `RevocationStore` завжди пам'ятає відкликане цим процесом.
- **D-57** Сценарії `packages/bench/scenarios/redis` імпортують бібліотеку відносним шляхом (`../../../redis/src`), бо `packages/bench/package.json` належить оркестратору. Плани процедур (`CALL` не обгортається `EXPLAIN`) збираються через `auto_explain` (рівень NOTICE, вкладені оператори) у транзакції з `ROLLBACK` — потрібен суперкористувач для `LOAD`. R1 «влучання» тримає кеш з TTL 1 год лише на час виміру; робочий TTL — 60 с. Сценарії R* не читають файл параметрів: входи виводяться з бази детерміновано (`ORDER BY id`).
